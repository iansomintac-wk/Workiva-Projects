WHAT WAS VERIFIED

tools/selfcheck.mjs — a headless Chrome runner added during this work.

  window.runSelfChecks()        366/366 passed, 0 failed
  window.runGuideSelfChecks()    18/18 passed, 0 failed

Neither page produced a console error or uncaught exception on load; the runner
subscribes to Runtime.exceptionThrown and fails the run if one appears.

THE TRACKER SUITE NEEDS A SEEDED BOOK. Re-measured for this record rather than
carried forward: on a fresh browser profile the suite reports 361/366, 5
failed — the phase3 health-score-pairing check, the v81 band check, and two
v94 Copilot checks. None are defects; each asserts on a populated book and
cannot be satisfied by an empty one. (The previous record's "314/354" for
this same measurement was already stale by the time it was superseded —
corrected here rather than carried forward unverified.)

The fifth unseeded failure, v74.4's whole-book-unchanged guard, is not a
"needs a seeded book" case, and fixing the defect first suspected of causing
it did not make it pass — that is stated plainly here rather than papered
over. What was fixed, and is fixed regardless: the v58 impact check restored
DATA.impact by `DATA.impact = savedImpact`, which — when savedImpact was
undefined because the key did not exist before the check ran — assigned an
OWN property set to undefined rather than leaving no property at all. Two
other places in this file that restore the same field already do it
correctly (v98's own impact check, and the identical impactLog restore one
line below the bug): capture presence before overwriting, then `delete` or
assign, never assign-through-undefined. Line 8206-8230 now matches that
shape. This was a real defect and stays fixed, but it was not sufficient:
the unseeded suite still reports 361/366, v74.4 still among the 5 failures,
identically — `removed=[] added=[impact] mutated=[]` — proving the v58
restore was not the (or not the only) trigger.

The actual trigger, found by wrapping DATA in a Proxy that logs a stack
trace on every write to `impact` and running the unseeded suite once more:
a Today-tab check (~line 8503) calls `renderToday()` directly to inspect its
output. That check already knows renderToday() has one side effect — it
stamps DATA.riskLog — and snapshots/restores exactly that field around the
call. It does not know about a second one: renderToday() -> renderDayClose()
-> computeImpactSummary() -> getImpactStore(), and getImpactStore() is
`if(!isRecordObject(DATA.impact)) DATA.impact = {...}` — a getter that
writes on read, the same shape v97's check already forbids for
getDayClose/getGainsightQueue/readSessionNote, just not for this one. On a
seeded book DATA.impact already exists, so the lazy-create is a no-op and
invisible; on an unseeded book it creates the key, and nothing near this
check knows to restore it. This is a second, distinct defect from the v58
one, in a different check, and it was not fixed here: the process for this
record was to name a defect precisely before touching more production code,
not to chain a second unauthorized fix onto the first. The runner therefore
evaluates demo-seed.js in the page before calling the suite:

  node tools/selfcheck.mjs osm-book-of-business-tracker-1.0.html \
       --seed demo-seed.js --expect 366
  node tools/selfcheck.mjs osm-runway-onboarding-1.0.html \
       --fn runGuideSelfChecks --expect 18

The August record did not state this, which is why its 318/318 was reproducible
only by accident.

A CORRECTION TO THE PREVIOUS RECORD
-----------------------------------
The August 6 record stated 318/318 and 18/18. All three of the following were
wrong or unreproducible, and two of them had been wrong when written.

1. THE TRACKER COUNT. 318 was true on August 6; by September 9 it was 354. It
   was also repeated in guide-manifest.json, README.txt and CHANGELOG.txt, so
   the same stale number was asserted in four places, one of them
   machine-readable.

2. THE GUIDE'S 18/18 WAS VIEWPORT-DEPENDENT, and nobody knew. The check named
   "quick mode actually removes the guided-only chapters" captured every
   .guided-only element and asserted all of them were visible after leaving
   quick mode. One of the nine is .chapter-dock, which the guide deliberately
   hides under 800px:

       @media (max-width: 800px) { .chapter-dock, .chapter-menu { display: none } }

   So the check passed in a real browser window and failed at any narrow width,
   while the guide behaved correctly at both. It reported 17/18 for the whole of
   this work before the cause was found. The check now captures each element's
   baseline display and asserts leaving quick mode restores every element to
   exactly that — stricter than the old assertion, and true at any width.

3. THE RUNNER NEVER PINNED A VIEWPORT, which is what allowed (2) to hide. Any
   check reading a computed style silently depended on whatever headless Chrome
   defaulted to — 782px — which is narrower than any window a human validating
   by hand would use. tools/selfcheck.mjs now pins 1440x900 and takes --width /
   --height so a viewport-sensitive check can be exercised deliberately.

The August record's own correction — that a manifest claimed 19 guide checks
when the suite had always reported 18 — was of exactly this species: a written
number that had never met the thing it described. Two more were found here.


WHAT WAS NOT VERIFIED
---------------------
THE MIGRATION HAS NOT RUN AGAINST A REAL BOOK. Every verification above used
synthetic fixtures. The dry run covered seven awkward shapes and lost nothing,
but a real 15-account book carries history no fixture reproduces. Export JSON
before opening this build against live data. The migration only ever adds, and
leaves sessionNotes intact, but it is a schema change against a store that has
no server copy and one level of undo.

Not exercised in this run:
  - Automatic backup end to end. Choosing a file, granting write permission and
    confirming a written payload all require user gestures and write to real
    disk. The suite asserts the three guards that stop the check suite from
    writing a fabricated book to a real backup file, and those pass, but no
    backup file was written or restored.
  - Any AI Copilot feature. These call the Anthropic API and need a key. The
    deterministic read was confirmed to render in full without one, with no
    console error — the degrade path works.
  - Gainsight CSV import against a real export.
  - Cross-browser behavior. Chrome only.
  - The Overview outcome panel remains read-only. Capture landed on the session
    card, where the OSM already ticks deliverables; the panel still only reports.
  - Nobody has ticked a box in a real browser against a real book. Every
    assertion above is a headless render or a direct function call.

-----------------------------
55 commits since 1.0 (git rev-list --count accc76e..6bd2695), counted through
6bd2695 — the commit that added this section. Every fix commit to this
record itself, landing after 6bd2695 (there are more than one by now — this

Two feature branches, both merged after a full-branch review, plus the fixes
that review produced.

TODAY TAB, PHASES 1-2 (suite 318 -> 324)
  - The day is ordered by priority, not by the clock: every call leads in clock
    order, then ranked work by severity, in two movements instead of five. The
    minutes arithmetic that spaced work between calls survives as a note on the
    beat rather than as page structure.
  - Gainsight admin moved from the third screen position to below the day.
  - Each beat states account state, up to four drivers, one recommended action
    and what is outstanding. The panel beside it keeps the evidence and drops
    the restatement.
  - Added tools/selfcheck.mjs: the gate became a command with an exit code
    rather than a console read.

OUTCOME CRITERIA AND EVIDENCE, PHASE A (suite 324 -> 345, schema 11 -> 12)
  - ADMIN_GAP_DEFS had said since it was written that "the numbered outcome is
    what graduation is judged against", and then checked a boolean. Success
    criteria now derive from each account's own curriculum, evidence is keyed by
    an opaque id assigned once, and outcomeVerdict() is pure and answers
    "unknown" where it does not know rather than "not ready".
  - The migration converts every historical tick into evidence without inventing
    a date it does not have.

UX AND CORRECTNESS FIXES (suite 345 -> 354)
  - The State label no longer contradicts the beat it sits on. It is now the
    worst of computeRisk and the account's ranked severity, so an account
    carrying a flagged escalation cannot read On Track. computeRisk itself is
    unchanged; only the label moved.
  - renewal_pressure declared severity:(c,sig) while every call site passes one
    argument, so its "past renewal" branch was unreachable and the signal was
    permanently capped at 3. An account whose graduation lands after its renewal
    scored identically to one merely approaching it. No test could have caught
    this — it returned a valid severity either way.
  - A health percentage no longer renders beside a state that does not derive
    from it.
  - The severity badge names its band ("Slipping") instead of numbering it
    ("Sev 3/4"), reusing the vocabulary STORY_CHAPTERS already defines.
  - The readiness strip no longer reads "Nothing is on the calendar" directly
    above "3 calls to prep".
  - The beat panel no longer states the same fact twice.
  - The Copilot band's SINCE date no longer runs the decode-scramble, which
    rendered a valid date as "SEP 9, 200&" mid-churn and read as corruption.

OUTCOME CRITERIA AND EVIDENCE, PHASE B (suite 354 -> 366)
  - The session deliverable checkbox writes evidence. Phase A shipped a store
    that nothing in the running app could write to; the only records that could
    exist were what the migration built from history. Ticking a box now records
    a date, an attribution, and the session's activity where one is logged.
  - sessionNotes[n].deliverables is left physically intact and is no longer read
    for meaning. A check asserts that writing to it changes nothing on screen.
  - First Value derives itself: every ttfv1 criterion evidenced gives an
    achieved date, taken from the LAST of them. A recorded date always wins.
    This CAN move the portfolio TTFV median. It does not move it in the demo
    book: measured, all 17 seeded accounts carry 9 ttfv1 criteria and 0
    evidence, so 0 accounts derive a date and portfolioTTFVStat is identical
    before and after at {median:125, n:12}. The path is exercised only by
    synthetic fixtures. On a real book with history it will move.
  - Cost of the derived path, measured rather than asserted:
    portfolioTTFVStat() over the 17-account book is 0.094 ms per call against
    roughly 0.002 ms for the equivalent plain field read. Both absolutes
    reproduce; the ratio between them does not — it divides two sub-millisecond
    numbers, and a re-measurement by a different reviewer landed on 57x against
    the same 0.094 ms. Read it as call-time negligible in absolute terms
    (0.094 ms), not as a precise multiplier. Stated so nobody later claims
    either direction.

A NOTE ON THE CHECKS THEMSELVES
-------------------------------
Six checks written during this work passed while asserting nothing, and each was
caught only because a rule was in force that a new check must be demonstrated
FAILING before it is accepted. Among them: a fixture that could not produce the
condition it tested, a scan that read past the region it meant to examine, a
comparison of unescaped text against escaped markup, and a CSRD fixture that
sampled the one deliverable label identical in both curricula.

A check that has never been seen to fail is not evidence. That rule is worth
keeping for anyone editing this file.
