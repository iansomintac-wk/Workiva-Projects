THE FIFTH UNSEEDED FAILURE IS FIXED. v74.4's whole-book-unchanged guard —
still present through the last two records despite two rounds of fixing
genuine defects that stopped short of closing it — is GONE from the
unseeded failure list as of this pass, closed with its own TDD check
rather than folded into a records-only pass. Root cause and history, now
that both are settled:

`getImpactStore()` (`if(!isRecordObject(DATA.impact)) DATA.impact =
{events:{}, since: todayISO()};`) was a getter that wrote DATA.impact on
first read when it didn't already exist — the same shape v97's check
already forbids for getDayClose/getGainsightQueue/readSessionNote, just
never extended to this one. `computeImpactSummary()`, which reads as a
pure summary function and is called from render paths that have no reason
to expect a write, called `getImpactStore()` and inherited the mutation.
Invisible on a seeded book, because DATA.impact already exists there;
obvious on an empty one, where merely asking "what did the tracker save
you" stamped a key nobody asked for.

Two self-checks were fixed in earlier rounds to restore DATA.impact by
presence rather than by value (capture whether the key existed before the
check ran; `delete` it if it did not, assign it back if it did — never
assign-through-undefined, which leaves an own property set to undefined
that Object.keys(DATA) still reports as added): the v58 impact check
(~line 8206) and a Today-tab check (~line 8503) that calls renderToday()
and had not known renderToday() -> renderDayClose() ->
computeImpactSummary() -> getImpactStore() also touches DATA.impact. A
later whole-branch-review pass corrected a false attribution of the
remaining failure to `v72 the day opens on the remembered beat, or the
first when there is none` (~line 8538): that check's two extra
renderToday() calls sit behind a guard that is TRUE on an unseeded book,
so they never execute on the run that produced `added=[impact]`. Measured
with a Proxy wrapping DATA and logging a stack trace on every `set` of
`impact`, the actual creator on that run was the v62 Today-cap check's
first renderToday() call (~line 8575) — the first of ten non-restoring
calls (of the suite's 13 total) to execute in file order, after which
DATA.impact already exists so no later call writes it. Both check-side
fixes were real and stayed; neither closed v74.4, because the leak was
never a property of any one call site. It was `getImpactStore()` itself,
called from a function with no business writing anything — the fourth
instance of the read-must-not-write family, and the only one of the four
still open.

THE v74.4 BLIND SPOT — MEASURED, THEN CLOSED THIS PASS. v74.4 is the
whole-book purity guard this record leans on to say the read/write split is
done, and it had a measured hole: it cannot detect a key leaked as an own
property mid-suite and cleared again before the suite ends. Its check runs
exactly once, at suite exit, comparing `Object.keys(DATA)` at entry against
`Object.keys(DATA)` now — a key that appears and disappears in between never
shows up in that diff.

Proved by mutation before the fix. On a scratch copy of the PRE-FIX,
368-check build, v101's restore-by-presence line — `if(hadImpact)
DATA.impact = JSON.parse(savedImpact); else delete DATA.impact;` — was
changed to the canonical assign-through-undefined bug this file has been
bitten by four times: `else DATA.impact = undefined;`. Re-running the
unseeded suite (`node tools/selfcheck.mjs <scratch copy> --expect 368`,
carrying the pre-fix count — the fix this paragraph is proving the need for
had not landed yet) afterward still reported the same four pre-existing
failures as the clean baseline (phase3, v81, both v94 checks) — 364/368 —
v74.4 did not fail; it stayed GREEN. Nothing in that run reported the
leaked key at all — that is the blind spot this section exists to document.
Two probe checks inserted around the leak, one right after v101's
`finally` and one right before v74.4 runs, had earlier shown why: immediately
after v101, `DATA.impact` is an own property (`hasOwnProperty: true`) with
`value: undefined` — the leak is real — but by the time v74.4 runs,
`hasOwnProperty: false`. Something between the two clears it before v74.4
ever gets a chance to see it as added. This meant "v74.4 is green" was
weaker evidence than earlier passes of this record had treated it as: it
ruled out a leak that survives to suite end, not one created and cleared
somewhere in the middle.

THE FIX, this pass: a mid-suite ownership checkpoint, `_recordKeyDivergence()`
(~line 7585, inside `_runSelfChecksInner`), called from the `check` closure
(~line 7597) after every one of the suite's ~369 calls. It compares
`Object.keys(DATA).sort()` against the suite-entry snapshot's key list —
read lazily inside the function, not captured at its own definition, since
the entry snapshot (`_bookAtSuiteEntry`, ~line 7620) is declared 35 lines
after `_recordKeyDivergence` but before any check() call actually runs —
and records which check ran and which keys were added or removed into a
local array. One new check, `v74.5 no check reports while the key set on
the book diverges from suite entry, in either direction, and the leak
recorder proves itself alive every run`, placed LAST in the suite (after
v74.4, because everything above must have had its chance to leak by then)
asserts that array stays empty AND that the recorder itself is provably
alive — see THE GUARD'S OWN LIVENESS PROOF below for the latter half,
added in a later pass than the rest of this section.

Built TDD: the new check was written and watched to fail BEFORE any other
line changed. Its first RED, on code nobody had touched yet, named `v58
impact: counts x default minutes, config override wins, total aggregates`
as the first offender, with `impactLog` as the added key — not `impact` and
`impactLog` both, as the family of four prior read-must-not-write defects
would have predicted: on a seeded book DATA already carries an own `impact`
property at suite entry, so assigning `undefined` to an EXISTING key never
changes `Object.keys`; only the newly-created `impactLog` key showed as a
divergence. Measured and reported as it came out, not adjusted to match the
prediction that motivated the work.

WHY v58 diverged: it calls `check(...)` INSIDE its `try`, and restores
`DATA.impact`, `DATA.config.impactMinutes` and `DATA.impactLog` in the
`finally` AFTERWARD — so at the moment it reports, the book is still
legitimately dirty by its own structure. Every other check in this suite
(the phaseA/phaseB blocks are the clearest example) computes `ok`/`detail`,
restores the book, THEN calls `check()`. v58's transient was never a data
defect — it restored correctly before this pass and restores correctly
now — but its structure was exactly the shape that would hide a real leak,
and it was the one thing standing between this suite and a strict mid-suite
guard. It was restructured to the suite's convention: compute `ok`/`detail`
inside the `try`, restore in the `finally`, call `check()` after the
`finally` has run. What it asserts, and the values it tests, are unchanged.
(A later pass, this record's own, found it had adopted only half the
sibling convention — `let ok=false, detail=''` with no `catch(err){ detail =
err.message; }`, so a throw inside its `try` would still abort the whole
suite. Added; no other change.)

WHAT THE NEW GUARD COVERS, AND WHAT IT DELIBERATELY DOES NOT. Scoped to the
book's OWN KEY SET only, not its values: diffing every field's value after
each of ~369 calls would be expensive and would duplicate a guard that
already exists. Value drift surviving to suite end remains v74.4's job. The
measured blind spot was an added (or removed) KEY that does not survive to
suite end, and closing that — plus proving, on every run, that the recorder
doing the closing is actually alive (see THE GUARD'S OWN LIVENESS PROOF
below) — is what v74.5 does.

PROOF THE GUARD BITES, post-fix, in one run. The same v101 scratch mutation
(`else DATA.impact = undefined;` in place of `else delete DATA.impact;`) was
re-applied to a fresh scratch copy of the fixed suite and run unseeded.
Re-measured against the CURRENT (post-liveness-probe) check: in that single
run, v74.5 went RED with `instrument alive=true; real leaks=201 — first
offender: v101 asking what the day saved you does not stamp a key onto the
book — added=[impact] removed=[]`. `impact` — not `impact` and `impactLog`
both, since this mutation only touches the `impact` restore line — is added
by v101 on an unseeded book (`hadImpact` false, so the mutated `else` branch
assigns `undefined` into a key that did not exist before) and stays an own
property, diverging from the suite-entry snapshot, on every one of the
checks that run after v101 until something downstream restores it by
value-based presence rather than `hasOwnProperty` — 201 of them, which is
why the count matters: a fixer reading `real leaks=1` versus `real
leaks=201` learns how far the leak traveled before something incidentally
cleaned it up. `instrument alive=true` here confirms the probe half is not
what's failing — the failure is the real leak, exactly as intended. v74.4
stayed GREEN in the very same run, exactly as it had before the fix — the
gap closed: v74.5 catches, live, what v74.4 structurally cannot catch at
all. The scratch copy was discarded immediately after.

THE GUARD'S OWN LIVENESS PROOF — ADDED THIS PASS. Everything above proves
v74.5 catches a real leak. It says nothing about whether the recorder
behind it could silently stop recording and leave v74.5 passing for the
wrong reason — an array that is empty because nothing leaked reads
identically to an array that is empty because nothing is watching. To close
that, the divergence-recording logic was factored out of the `check`
closure into its own named function, `_recordKeyDivergence()` (~line 7585),
so it can be invoked directly as well as per-check. Immediately before its
own `check()` call, v74.5 now stamps a probe key onto DATA
(`DATA.__v745LivenessProbe = true`), calls `_recordKeyDivergence()` by hand
with a label no real check uses, deletes the probe key, and asserts the
recorder captured exactly that probe naming exactly that key — a check that
passes only if the instrument that is supposed to be running for the
other ~369 calls actually ran for this one too. The probe key is gone
before `check()` returns, so it is invisible to v74.4 (which in any case
already ran, above v74.5, in file order) and to any other check.

Proved by forcing the recorder dead. On a scratch copy, `_recordKeyDivergence`'s
body was changed to `if (false && keysNow !== _bookAtSuiteEntry.__keys) {`,
so it can never push a divergence regardless of what DATA does. Run seeded
(`node tools/selfcheck.mjs <scratch copy> --seed demo-seed.js --expect
369`):

  runSelfChecks: 368/369 passed, 1 failed
    FAIL  v74.5 no check reports while the key set on the book diverges
    from suite entry, in either direction, and the leak recorder proves
    itself alive every run — instrument alive=false (DEAD — probe was not
    recorded); real leaks=0

`real leaks=0` here is the trap this proof exists to catch: a dead recorder
and a clean book produce the exact same evidence a working recorder and a
clean book would (an empty `_midSuiteLeaks`) — `instrument alive=false` is
the only thing in that output telling a reader the zero is meaningless. The
scratch copy was discarded immediately after.

A CORRECTION TO THE PREVIOUS RECORD
-----------------------------------
The August 6 record stated 318/318 and 18/18. All three of the following were
wrong or unreproducible, and two of them had been wrong when written.

1. THE TRACKER COUNT. 318 was true on August 6; by September 9 it was 354. It
   was also repeated in guide-manifest.json, README.txt and CHANGELOG.txt, so
   the same stale number was asserted in four places, one of them
   machine-readable.

2. THE GUIDE'S 18/18 WAS VIEWPORT-DEPENDENT, and nobody knew. The check named
   "quick mode actually removes the guided-only chapters" captured every
   .guided-only element and asserted all of them were visible after leaving
   quick mode. One of the nine is .chapter-dock, which the guide deliberately
   hides under 800px:

       @media (max-width: 800px) { .chapter-dock, .chapter-menu { display: none } }

   So the check passed in a real browser window and failed at any narrow width,
   while the guide behaved correctly at both. It reported 17/18 for the whole of
   this work before the cause was found. The check now captures each element's
   baseline display and asserts leaving quick mode restores every element to
   exactly that — stricter than the old assertion, and true at any width.

3. THE RUNNER NEVER PINNED A VIEWPORT, which is what allowed (2) to hide. Any
   check reading a computed style silently depended on whatever headless Chrome
   defaulted to — 782px — which is narrower than any window a human validating
   by hand would use. tools/selfcheck.mjs now pins 1440x900 and takes --width /
   --height so a viewport-sensitive check can be exercised deliberately.

The August record's own correction — that a manifest claimed 19 guide checks
when the suite had always reported 18 — was of exactly this species: a written
number that had never met the thing it described. Two more were found here.

Not exercised in this run:

    writing a fabricated book to a real backup file, and those pass, but no
    backup file was written or restored.

    deterministic read was confirmed to render in full without one, with no
    console error — the degrade path works.
  - Gainsight CSV import against a real export.
  - Cross-browser behavior. Chrome only.
  - The Overview outcome panel remains read-only. Capture landed on the session
    card, where the OSM already ticks deliverables; the panel still only reports.
  - Nobody has ticked a box in a real browser against a real book. Every
    assertion above is a headless render or a direct function call.
  - THE TWO DOM LISTENERS ADDED THIS PHASE HAVE NO COVERAGE, AND AN ATTEMPT
    WAS MADE AND ABANDONED, NOT SKIPPED. The two `change` listeners at
    `$$('[data-session-deliverable]')` and `$$('[data-deliverable-by]')`
    (~line 22124 and ~line 22141) are thin DOM adapters — `split('|')`,
    `parseInt`, the call into the already-covered `toggleDeliverableEvidence`
    / `reattributeDeliverableEvidence`, the `saveData()` call, and the
    `bySel.disabled` / `.value` patching. The logic functions they call ARE
    covered; the adapter itself is not. Reaching it honestly means calling
    the actual `attachEvents()` (the closures under test only exist inside
    it) against a real, `document`-attached checkbox, with a real dispatched
    `change` event — not a copy of the listener body pasted into a check
    (which would stop testing the shipped code the moment the two diverged)
    and not a `.toString()` scan for `saveData` (the exact decorative-check
    failure mode this branch has already caught ten times). `attachEvents()`
    is global and unscoped: it re-binds every selector it touches — dozens,
    across the whole app, not just these two — over whatever is CURRENTLY in
    `document`. Calling it from a self-check without first replacing that
    DOM wholesale (the real `render()`'s job, which also calls
    `syncRoute()` and moves keyboard focus) risks a second, duplicate
    listener stacked onto the live page's real, currently-bound elements —
    contamination the suite cannot detect or undo the way it can restore a
    `DATA` snapshot. That is a materially different and larger risk than
    anything else in this suite touches, so no check was written rather than
    force one through. Measured instead, per the instruction to measure the
    gap rather than assert it away: removing `saveData();` from BOTH
    listeners and running `node tools/selfcheck.mjs
    osm-book-of-business-tracker-1.0.html --seed demo-seed.js --expect 369`
    still reports `369/369 passed, 0 failed`, exit 0 (re-measured against
    this record's own suite count — now 369, after v74.5 — and reverted
    immediately after; the earlier record of this same measurement had
    said 368 and gone stale the moment v74.5 shipped). The gap itself is
    unchanged; only those numbers were.
    Concretely, this costs a user: tick a deliverable
    box, watch it render checked, close the tab or reload without another
    save-triggering action — the tick is gone. The evidence store update
    happened in memory (`toggleDeliverableEvidence` IS covered and IS
    correct) and was never persisted. The fix is not more test cleverness;
    it is a way to exercise a real DOM adapter without touching the live
    app's actual bound state, which does not exist in this codebase yet.
  - THE GUIDE DOES NOT TEACH PHASE B. osm-runway-onboarding-1.0.html is
    byte-identical to before this branch — the one commit that touched it
    fixed a self-check's viewport assertion, not content. Its First Value
    narrative still describes the pre-Phase-B "earliest linked evidence"
    model; it does not cover the deliverable-checkbox evidence capture, the
    customer-demonstrated / we-observed attribution control, or First
    Value's derived path. Updating it is outstanding, real authoring work,
    not done as part of this record.

A NOTE ON THE CHECKS THEMSELVES
-------------------------------
Six checks written during this work passed while asserting nothing, and each was
caught only because a rule was in force that a new check must be demonstrated
FAILING before it is accepted. Among them: a fixture that could not produce the
condition it tested, a scan that read past the region it meant to examine, a
comparison of unescaped text against escaped markup, and a CSRD fixture that
sampled the one deliverable label identical in both curricula.

A check that has never been seen to fail is not evidence. That rule is worth
keeping for anyone editing this file.
