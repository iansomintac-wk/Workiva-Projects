The fifth unseeded failure, v74.4's whole-book-unchanged guard, is STILL
present after two rounds of fixing genuine defects that stop short of
closing it. Stated plainly rather than adjusted to fit: the unseeded suite
is still 362/367, v74.4 still fails, still `removed=[] added=[impact]

getImpactStore() (`if(!isRecordObject(DATA.impact)) DATA.impact = {...}`) is
a getter that writes DATA.impact on first read when it doesn't already
exist — the same shape v97's check already forbids for
getDayClose/getGainsightQueue/readSessionNote, just not extended to this
one. Invisible on a seeded book, because DATA.impact already exists there.
Two DIFFERENT self-checks trigger it on an unseeded book and have both now
been fixed to restore by presence (capture whether the key existed before
the check ran; `delete` it if it did not, assign it back if it did — never
assign-through-undefined, which leaves an own property set to undefined
that Object.keys(DATA) reports as added):
  1. The v58 impact check (~line 8206) — its OWN restore of the field it
     was directly testing was wrong. Fixed round 1.
  2. A Today-tab check (~line 8503) that calls renderToday() to inspect its
     HTML output. It already knew renderToday() stamps DATA.riskLog and
     restored that; it did not know renderToday() -> renderDayClose() ->
     computeImpactSummary() -> getImpactStore() also touches DATA.impact.
     Fixed round 2.
Both fixes are real, independently verified (each one's own check still
passes; the seeded suite, 366/366 at the time these two rounds were done —
before this record's own suite count moved to 367 — stayed 366/366 across
both), and stay. Neither was sufficient alone or together: the unseeded
figure did not move after either round.

CORRECTION (whole-branch review fix wave). The previous text here named a
THIRD SITE — `v72 the day opens on the remembered beat, or the first when
there is none` (~line 8538) — as the remaining cause. That attribution was
false, and is corrected in place rather than left to stand: v72's two extra
renderToday() calls (lines 8539 and 8544) sit behind
`if(!again.length && !callsScheduledToday().length)` (line 8522), and that
guard is TRUE on an unseeded book — confirmed by seeding a one-line probe
that reads `todayActionList().length` and `callsScheduledToday().length`
directly and got `{againLen:0, scheduledLen:0, guardTrue:true}`. v72's own
branch is never entered on the run that produces `added=[impact]`; its two
calls contribute nothing to it.

This was never a single third SITE — it is a CLASS. The suite contains
exactly 13 renderToday() calls (counted directly: lines 8512, 8539, 8544,
8575, 8578, 8656, 8688, 8917, 10678, 10740, 10871, 10873, 10896). Of those,
exactly ONE — line 8512, the Today-tab check fixed above — restores
DATA.impact. Two (8539, 8544, both v72's) are gated behind the guard just
confirmed true and never execute on an unseeded run. The remaining TEN fire
without any DATA.impact restore and belong to the same defect class as the
two already-fixed sites: the v62 Today-cap check (8575, 8578), the v69
"removed surfaces" check (8656), the phase1 "Records to bring up to date"
check (8688), and six more v72 day-timeline checks (8917, 10678, 10740,
10871, 10873, 10896).

Which of those ten actually CREATES the leaked key was measured, not
assumed, with a Proxy wrapping DATA and logging a stack trace on every
`set` of `impact` across a full unseeded run. Exactly four writes occur in
the whole suite: the v58 check's own two (its internal test of
trackImpact(), both expected and both cleaned up by its own restore), and
one real creation — at line 8575, the v62 Today-cap check's first
renderToday() call, the first of the ten non-restoring calls to execute in
file order. From that point on DATA.impact is a real object, so
`getImpactStore()`'s `if(!isRecordObject(DATA.impact))` guard is false for
every later call and none of the other nine — phase1's check (8688)
included — performs a further write; the trace shows no `set` event at any
of them. They are equally defective (each would independently leak the key
if it ran first against a clean book, and fixing 8575 alone would just
hand the same failure to line 8656, the next one in file order) but on THIS
measured run only line 8575 is the actual creator.

Root cause, not the symptom: `getImpactStore()` (lines 15800-15805,
`if(!isRecordObject(DATA.impact)) DATA.impact = {events:{}, since:
todayISO()};`) is a getter that writes on first read — the same shape v97's
own check already forbids for getDayClose/getGainsightQueue/readSessionNote,
just never extended to this one. `computeImpactSummary()` (line 15871),
which reads as a pure summary function and is called from render paths that
have no reason to expect a write, calls `getImpactStore()` and inherits the
mutation. A measured fix exists and is NOT applied in this pass: a six-line
`readImpactStore()` (a pure read returning `DATA.impact.events`/`.since`
with in-memory defaults, never assigning to DATA) with
`computeImpactSummary()` pointed at it was measured, against the 366-check
baseline that stood before this record's own new check, to take the
unseeded suite from 361/366 to 362/366 with v74.4 green, and to leave the
seeded suite unchanged at 366/366. The suite is 367 now (this wave added
one check, in item 2 below) — re-baseline against 367 rather than assuming
the 361/362 pair still applies verbatim; the mechanism and the +1 shift are
what's confirmed, not the exact digits against a count that has since
moved. It needs its own TDD pass — a red-flip check demonstrating the leak,
then the fix, then green — so it is deferred to a follow-up task with its
own check, not folded into a records-only pass. The runner therefore still

A CORRECTION TO THE PREVIOUS RECORD
-----------------------------------
The August 6 record stated 318/318 and 18/18. All three of the following were
wrong or unreproducible, and two of them had been wrong when written.

1. THE TRACKER COUNT. 318 was true on August 6; by September 9 it was 354. It
   was also repeated in guide-manifest.json, README.txt and CHANGELOG.txt, so
   the same stale number was asserted in four places, one of them
   machine-readable.

2. THE GUIDE'S 18/18 WAS VIEWPORT-DEPENDENT, and nobody knew. The check named
   "quick mode actually removes the guided-only chapters" captured every
   .guided-only element and asserted all of them were visible after leaving
   quick mode. One of the nine is .chapter-dock, which the guide deliberately
   hides under 800px:

       @media (max-width: 800px) { .chapter-dock, .chapter-menu { display: none } }

   So the check passed in a real browser window and failed at any narrow width,
   while the guide behaved correctly at both. It reported 17/18 for the whole of
   this work before the cause was found. The check now captures each element's
   baseline display and asserts leaving quick mode restores every element to
   exactly that — stricter than the old assertion, and true at any width.

3. THE RUNNER NEVER PINNED A VIEWPORT, which is what allowed (2) to hide. Any
   check reading a computed style silently depended on whatever headless Chrome
   defaulted to — 782px — which is narrower than any window a human validating
   by hand would use. tools/selfcheck.mjs now pins 1440x900 and takes --width /
   --height so a viewport-sensitive check can be exercised deliberately.

The August record's own correction — that a manifest claimed 19 guide checks
when the suite had always reported 18 — was of exactly this species: a written
number that had never met the thing it described. Two more were found here.


WHAT WAS NOT VERIFIED
---------------------
THE MIGRATION HAS NOT RUN AGAINST A REAL BOOK. Every verification above used
synthetic fixtures. The dry run covered seven awkward shapes and lost nothing,
but a real 15-account book carries history no fixture reproduces. Export JSON
before opening this build against live data. The migration only ever adds, and
leaves sessionNotes intact, but it is a schema change against a store that has
no server copy and one level of undo.

Not exercised in this run:
  - Automatic backup end to end. Choosing a file, granting write permission and
    confirming a written payload all require user gestures and write to real
    disk. The suite asserts the three guards that stop the check suite from
    writing a fabricated book to a real backup file, and those pass, but no
    backup file was written or restored.
  - Any AI Copilot feature. These call the Anthropic API and need a key. The
    deterministic read was confirmed to render in full without one, with no
    console error — the degrade path works.
  - Gainsight CSV import against a real export.
  - Cross-browser behavior. Chrome only.
  - The Overview outcome panel remains read-only. Capture landed on the session
    card, where the OSM already ticks deliverables; the panel still only reports.
  - Nobody has ticked a box in a real browser against a real book. Every
    assertion above is a headless render or a direct function call.
  - THE TWO DOM LISTENERS ADDED THIS PHASE HAVE NO COVERAGE, AND AN ATTEMPT
    WAS MADE AND ABANDONED, NOT SKIPPED. The two `change` listeners at
    `$$('[data-session-deliverable]')` and `$$('[data-deliverable-by]')`
    (~line 21995 and ~line 22012) are thin DOM adapters — `split('|')`,
    `parseInt`, the call into the already-covered `toggleDeliverableEvidence`
    / `reattributeDeliverableEvidence`, the `saveData()` call, and the
    `bySel.disabled` / `.value` patching. The logic functions they call ARE
    covered; the adapter itself is not. Reaching it honestly means calling
    the actual `attachEvents()` (the closures under test only exist inside
    it) against a real, `document`-attached checkbox, with a real dispatched
    `change` event — not a copy of the listener body pasted into a check
    (which would stop testing the shipped code the moment the two diverged)
    and not a `.toString()` scan for `saveData` (the exact decorative-check
    failure mode this branch has already caught ten times). `attachEvents()`
    is global and unscoped: it re-binds every selector it touches — dozens,
    across the whole app, not just these two — over whatever is CURRENTLY in
    `document`. Calling it from a self-check without first replacing that
    DOM wholesale (the real `render()`'s job, which also calls
    `syncRoute()` and moves keyboard focus) risks a second, duplicate
    listener stacked onto the live page's real, currently-bound elements —
    contamination the suite cannot detect or undo the way it can restore a
    `DATA` snapshot. That is a materially different and larger risk than
    anything else in this suite touches, so no check was written rather than
    force one through. Measured instead, per the instruction to measure the
    gap rather than assert it away: removing `saveData();` from BOTH
    listeners and running `node tools/selfcheck.mjs
    osm-book-of-business-tracker-1.0.html --seed demo-seed.js --expect 367`
    still reports `367/367 passed, 0 failed`, exit 0 (reverted immediately
    after measuring). Concretely, this costs a user: tick a deliverable
    box, watch it render checked, close the tab or reload without another
    save-triggering action — the tick is gone. The evidence store update
    happened in memory (`toggleDeliverableEvidence` IS covered and IS
    correct) and was never persisted. The fix is not more test cleverness;
    it is a way to exercise a real DOM adapter without touching the live
    app's actual bound state, which does not exist in this codebase yet.
  - THE GUIDE DOES NOT TEACH PHASE B. osm-runway-onboarding-1.0.html is
    byte-identical to before this branch — the one commit that touched it
    fixed a self-check's viewport assertion, not content. Its First Value
    narrative still describes the pre-Phase-B "earliest linked evidence"
    model; it does not cover the deliverable-checkbox evidence capture, the
    customer-demonstrated / we-observed attribution control, or First
    Value's derived path. Updating it is outstanding, real authoring work,
    not done as part of this record.

OUTCOME CRITERIA AND EVIDENCE, PHASE A (suite 324 -> 345, schema 11 -> 12)
  - ADMIN_GAP_DEFS had said since it was written that "the numbered outcome is
    what graduation is judged against", and then checked a boolean. Success

  - The migration converts every historical tick into evidence without inventing

UX AND CORRECTNESS FIXES (suite 345 -> 354)
  - The State label no longer contradicts the beat it sits on. It is now the
    worst of computeRisk and the account's ranked severity, so an account

  - renewal_pressure declared severity:(c,sig) while every call site passes one

    from it.
  - The severity badge names its band ("Slipping") instead of numbering it
    ("Sev 3/4"), reusing the vocabulary STORY_CHAPTERS already defines.
  - The readiness strip no longer reads "Nothing is on the calendar" directly
    above "3 calls to prep".
  - The beat panel no longer states the same fact twice.
  - The Copilot band's SINCE date no longer runs the decode-scramble, which
    rendered a valid date as "SEP 9, 200&" mid-churn and read as corruption.

OUTCOME CRITERIA AND EVIDENCE, PHASE B (suite 354 -> 366)
  - The session deliverable checkbox writes evidence. Phase A shipped a store
    that nothing in the running app could write to; the only records that could
    exist were what the migration built from history. Ticking a box now records
    a date, an attribution, and the session's activity where one is logged.
  - sessionNotes[n].deliverables is left physically intact and is no longer read
    for meaning. A check asserts that writing to it changes nothing on screen.
  - First Value derives itself: every ttfv1 criterion evidenced gives an
    achieved date, taken from the LAST of them. A recorded date always wins.
    This CAN move the portfolio TTFV median. It does not move it in the demo
    book: measured, all 17 seeded accounts carry 9 ttfv1 criteria and 0
    evidence, so 0 accounts derive a date and portfolioTTFVStat is identical
    before and after at {median:125, n:12}. The path is exercised only by
    synthetic fixtures. On a real book with history it will move.
  - Cost of the derived path, measured rather than asserted:
    portfolioTTFVStat() over the 17-account book is 0.094 ms per call against
    roughly 0.002 ms for the equivalent plain field read. Both absolutes
    reproduce; the ratio between them does not — it divides two sub-millisecond
    numbers, and a re-measurement by a different reviewer landed on 57x against
    the same 0.094 ms. Read it as call-time negligible in absolute terms
    (0.094 ms), not as a precise multiplier. Stated so nobody later claims
    either direction.

A NOTE ON THE CHECKS THEMSELVES
-------------------------------
Six checks written during this work passed while asserting nothing, and each was
caught only because a rule was in force that a new check must be demonstrated
FAILING before it is accepted. Among them: a fixture that could not produce the
condition it tested, a scan that read past the region it meant to examine, a
comparison of unescaped text against escaped markup, and a CSRD fixture that
sampled the one deliverable label identical in both curricula.

A check that has never been seen to fail is not evidence. That rule is worth
keeping for anyone editing this file.
