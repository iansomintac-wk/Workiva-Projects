## 3. Design

### 3.1 Storage and reading (part 1)

1. New IndexedDB database `obm-transcripts-v1`, one object store, one record per transcript version: `{ref, activityId, text, chars, sha1, savedAt}`. `ref` = `<activityId>:<first 12 hex of sha1>` (one key per version; see 3.2). `sha1` = SHA-1 of the UTF-8 bytes of `text`, hex.
2. The activity keeps `transcript: {ref, chars, sha1, truncated}`. `truncated` is true only for a transcript an older version already cut; nothing new is cut.
3. At startup, after `loadData`, every referenced record is read into an in-memory map. `activityTranscript` returns `{text, truncated}` from that map, so its four callers stay synchronous and unchanged in shape.
4. Never cut what is stored. The four writers in section 2 stop cutting. The 120K cap applies only where text is sent to the AI (the debrief), to `recordSent` as a whole, with the existing visible "truncated" marker, so quote verification still runs against exactly what was sent. The 4 MB file-read limit in `readTranscriptFile` stays.
5. Saving order: write the record, read it back and check its SHA-1, then commit the book with the reference. If the book commit fails, delete the new record. A transcript never looks saved without being saved.
6. Remove deletes the record and clears the undo slot. Replace writes the new version under its own `ref`, commits, then deletes the old record and clears the undo slot. Undo can never restore a reference to a deleted record.

### 3.2 Move, backups, failure (part 2)

7. Schema 16 -> 17. In `loadData`, after `migrateData`: each activity whose `transcript.text` is still inline is written to IndexedDB, read back and checked, then replaced by its reference; the book is saved once at the end. The untouched original book string is stored first in IndexedDB (store `premigration`, keyed by date), not in localStorage. Because `ref` is derived from the text, two tabs moving at once write the same records.
8. If IndexedDB cannot be opened, nothing moves and no error blocks the load. `activityTranscript` reads both forms: inline `{text, truncated}` (old) and `{ref, ...}` (new).
9. Export, backup file and archive each write one JSON file: the book as today plus a top-level `transcripts` object `{ref: text}` holding every transcript the book (or the archived customer) references.
10. Backup preparation: the `transcripts` part of the backup is serialized once and cached; it is rebuilt only when a transcript is added, replaced or removed. Each backup write re-serializes only the book.
11. Archive keeps the archived customer's records in IndexedDB (they leave the book's backup because nothing references them) and writes them into the archive file. Archive restore re-links them; if they are absent, it writes them from the file.
12. Import and archive restore accept both file shapes: with a `transcripts` object (new), or inline `transcript.text` (old, moved on the way in by the same path as 7). Records are written and checked before the book is committed. Step 0's rule stands: a synthetic book is refused over a stored real one.
13. Failure is visible: a reference whose record is missing, or whose text fails its SHA-1, shows "Transcript missing from this browser - restore from a backup" on the activity; View is disabled; the debrief sends no transcript text. The book still loads.
14. Unlinked records (from a stale tab saving over a newer book, or from archive) are kept, never deleted automatically.
15. One-way for 1.0 (read): once 1.1 has moved a book to schema 17, 1.0 refuses to load it ("schema v17 is newer than this tracker supports", `osm-book-of-business-tracker-1.0.html` 18071; the rejected-load guard keeps it from overwriting). A code revert does not undo the move. The way back is an export made before the first open of the new 1.1; Ian's slip makes that his step (run prompt, "Backup step").

## 6. Changes from DESIGN 5

- DESIGN: records keyed by activity id. Here: one key per version (`<activityId>:<sha1 prefix>`), so a failed Replace cannot delete the transcript it was replacing and two tabs moving at once do not collide.
- DESIGN: the 4 MB file limit applies only to what is sent to the AI. Here: it stays as a sanity guard on reading a file.
- DESIGN: the original book kept under a dated side key (as `-prerepair-`). Here: kept in IndexedDB, because a second full copy in localStorage can exceed the 5,242,308-character limit.
- DESIGN check "50 maximum-size transcripts". Here: 50 x 160K; at the old 120K cap such a book (6.0M characters) could not exist in localStorage at all.
- Added: in-memory load at startup, backup preparation cache, archive keeps records, visible missing state.
